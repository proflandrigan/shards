# Release guide

Status: **OPEN. Nothing has been published.** The 2.0.0-next.0 packages exist only locally. Publishing is an external step that has not been done.

## Two-package layout

| Package | Source | Purpose |
|---|---|---|
| `@proflandrigan/shards` (root) | `package.json` at the repo root | Self-contained CLI and installer. Ships `cli/`, `build/`, `core/`, `hooks/`, `runtime/`, `bindings/`, `src/commands/`, `src/docs/`, the deprecated `tools/` bins (and the v1 installer), and `README.md`. The exact allow-list is enforced by `scripts/pack-check.js`. |
| `@proflandrigan/shards-mcp` (staged) | Generated by `scripts/stage-runtime-package.js` | MCP runtime only (gates, sessions, agent loading). Bin `shards-mcp` -> `runtime/server.js`. |

The staged package is never hand-edited. Its `package.json` is generated by `releasePackageJson('mcp')` in `build/package.js` (the same function generates the private plugin `package.json` with `'plugin'`) from the root manifest: same `version`, same `dependencies`, the name and bin above, and `publishConfig` with `access: public` and `tag: next`.

The stage script copies `runtime/`, `core/`, `bindings/`, `hooks/lib/`, `build/`, and `scripts/validate-agents.js` into a directory, keeping repo-relative paths so the runtime's `../core`, `../bindings`, `../hooks/lib`, and `../package.json` requires resolve unchanged.

```bash
node scripts/stage-runtime-package.js --out <dir>   # prints the staged dir
```

Without `--out` it stages into a fresh directory under `os.tmpdir()`.

## Versions and dist-tag

- Both packages are versioned `2.0.0-next.0` (the root version is the source for the staged package).
- `publishConfig.tag` is `next` in both manifests. An accidental `npm publish` therefore lands on the `next` tag and never moves `latest`.
- The dry run enforces this: it fails if `publishConfig.tag` is not `next` or the version does not match `^2\.0\.0-next\.\d+$`.

## Deprecated v1 bins (E10.5 prep)

The root `bin` map keeps `shards-ui`, `shards-gates` and `shards-sessions` (under `tools/`) through the 2.0 next line, but they are now thin deprecation shims. Do not remove them yet.

| v1 command | Behaviour now |
|---|---|
| `shards-gates <sub>` | stderr notice, then forwards to `shards gates <sub>` (exact equivalent; bare `force-close` still maps to `--all`) |
| `shards-sessions <sub>` | stderr notice, then forwards to `shards sessions <sub>`; v1-only flags (`--agent`, `--project`) now exit 2 |
| `shards-ui` | prints the Studio replacement (`npx @proflandrigan/shards-studio`); `status`/`stop`/`help` exit 0, anything that tried to start the UI exits 1 |
| `node tools/install.js` (install) | prints the v2 replacements (`shards build --target claude --dev`, the marketplace install, `shards install --project`, `--agents-md`, `--claude-md`) and exits 1 without writing anything; `--legacy` or `SHARDS_LEGACY_INSTALL=1` runs the old unsupported install |
| `node tools/install.js uninstall` | still works, so a v1 install can be removed |

Removal is the E10.5 step itself and is out of scope here.

## Rule: new runtime requires that escape `runtime/`

If runtime code under `runtime/` gains a `require` that reaches outside `runtime/` (for example a new `../something`), you must do both of these in the same change:

1. Add the target to the copy list in `scripts/stage-runtime-package.js` (the `for (const d of [...])` list, or the `scripts/validate-agents.js` copy). Otherwise the staged package will be missing the file.
2. Add the path to `MCP_FILES` in `build/package.js` (the staged package's `files` list) and to `KINDS.mcp` (`allowed` and `required`) in `scripts/pack-check.js`. Likewise a new top-level path in the root tarball goes in package.json `files` and `KINDS.cli`.

If you skip this, the staged tarball will break at runtime, or pack-check will fail on an unexpected, missing or required-but-unpacked file.

## What `scripts/release-dry-run.sh` checks

Run with `npm run release:dry-run` or `bash scripts/release-dry-run.sh`. Set `KEEP=1` to keep the scratch directory. It never publishes.

1. **Pack**: `npm pack` the root, stage the MCP package, and `npm pack` that too.
2. **Contents**: `scripts/pack-check.js` (also `npm run pack:check`, run in `ci.yml` and `release.yml`) checks that every file in each tarball is in the explicit allow-list, no forbidden file (tests, `node_modules`, `.claude/`) is present, every required path is present, every `bin` target is packed, and the transitive relative-`require` closure of every bin, `runtime/server.js` and `hooks/*.js` is packed. A bin that starts requiring an unshipped file fails here.
3. **Manifests**: each package's bins exist and are executable, `publishConfig.tag` is `next`, and the version matches `2.0.0-next.N`.
4. **Fresh install**: both tarballs install into a clean project. If the registry install fails, it retries offline, then falls back to extracted tarballs with symlinked `node_modules` (the script prints the mode it used; in fallback mode dependencies are not verified from the registry).
5. **CLI**: `shards --help` lists exactly `build`, `doctor`, `gates`, `install`, `migrate`, `sessions`, `uninstall-dev`.
6. **Doctor**: `shards doctor` runs in an empty non-git directory and does not return a failure.
7. **Build**: `shards build --target claude --dev` from the installed package produces `.mcp.json` and `hooks/hooks.json`, and the MCP and hook paths point at files that exist inside the installed package.
8. **Deprecated bins**: `shards-gates`, `shards-sessions`, `shards-ui` and `tools/install.js` each print their v2 replacement.
8b. **Validate**: when the `claude` CLI is on PATH, `claude plugin validate --strict` passes for the generated plugin (directory profile) and marketplace.
9. **MCP smoke**: `scripts/mcp-smoke-client.js` starts `shards-mcp` over stdio, runs `initialize` and `tools/list`, and asserts `activate` and `gate_request` are present.

Result is `RESULT: PASS` or `RESULT: FAIL (n step(s) failed)`.

## Claude Code release plugin (E7.1, E7.4 to E7.6)

`shards build --target claude` without `--dev` emits a complete, self-contained plugin (dev mode is unchanged):

```
.claude-plugin/plugin.json   name shards, version, description, author, license, repository, homepage, keywords, icon
.mcp.json                    node ${CLAUDE_PLUGIN_ROOT}/runtime/server.js, env SHARDS_PROJECT_ROOT=${CLAUDE_PROJECT_DIR}
hooks/hooks.json             hooks/claude-code.hooks.json verbatim (${CLAUDE_PLUGIN_ROOT}/hooks/<shim>.js)
hooks/*.js hooks/lib/        hook shims
runtime/ core/ bindings/ build/ scripts/validate-agents.js
package.json                 name, version, dependencies only (private; build/package.js releasePackageJson('plugin'))
assets/icon.png              512x512 square icon (build/assets/icon.png, made from shards_icon.png); plugin.json `icon` points at it
node_modules/                production dependency closure only (~28MB), resolved from the repo's node_modules, no network
skills/ agents/ content/ README.md size-report.json
```

`skills/` holds one switch skill per switchable agent plus the utility skills (`agents`, `brainstorm`, `review-pr`, `notebook-walkthrough`, `resume`, `end`, `shards-conventions`) generated by `build/skills.js`. `agents/` holds the consult subagents (`<agent>.md` and `<agent>-<entry>.md`; no `model` key, no `Task`/`Agent` tools).

Build it:

```bash
node cli/shards.js build --target claude --out <dir>                  # plugin only
node cli/shards.js build --target claude --no-bundle-deps --out <dir> # skip node_modules (fast; not runnable)
node cli/shards.js build --target claude --marketplace --out <root>   # <root>/.claude-plugin/marketplace.json + <root>/plugins/shards
claude plugin validate --strict <root>/plugins/shards && claude plugin validate --strict <root>
```

Optional default agent (E7.7, off by default): `--default-agent` (or `SHARDS_BUILD_DEFAULT_AGENT=1`) additionally emits plugin-root `settings.json` `{"agent":"shards:syn"}` and drops `tools` from `agents/syn.md` so Syn can run as the main thread. Compat CC-3: `claude plugin validate --strict` still passes but warns that a plugin's `agent` setting "is deprecated and will stop applying in a future release". The recommended activation is therefore `claude --agent shards:syn`, or a project `.claude/settings.json` containing `{"agent":"shards:syn"}`. Do not rely on the plugin `settings.json`.

The repo-root `.claude-plugin/marketplace.json` is generated by `build/package.js` (`marketplaceText()`) and committed; `test/release-plugin.test.js` fails if it drifts. `plugins/` is gitignored.

### Distribution: how `/plugin marketplace add proflandrigan/shards` resolves the plugin (E10.4, ADR 0012)

The repo-root `.claude-plugin/marketplace.json` (committed, on the default branch) lists the plugin with a `github` source: `{ "source": "github", "repo": "proflandrigan/shards", "ref": "marketplace" }`. `.github/workflows/release.yml` builds the plugin and force-pushes it as the root of a single-commit `marketplace` branch. `shards build --marketplace` writes the local variant (`./plugins/shards`) used for offline `claude plugin validate`. `plugins/` stays gitignored.

Users install with:

```
/plugin marketplace add proflandrigan/shards
/plugin install shards@shards
```

## Release workflow (`.github/workflows/release.yml`)

Triggers: push of a `v*` tag, or `workflow_dispatch`. Default permissions are `contents: read`.

| Job | Runs | Does |
|---|---|---|
| `verify` | always | checks the tag equals `v<version>`, runs tests, lints, coupling ratchet, `npm run pack:check`, `npm run release:dry-run` |
| `build` | after verify | builds claude (`--marketplace`), codex and skills; packs and pack-checks both npm tarballs; archives each target; uploads `release-packages` and `plugin-tree` artifacts |
| `github-release` | tags only, `contents: write` | `gh release create` with all archives and tarballs attached (pre-release if the tag has a `-` suffix) |
| `marketplace-branch` | tags, or dispatch with `push_marketplace: true`; `contents: write` | force-pushes the plugin tree to the `marketplace` branch |
| `npm-publish` | only if repo variable `SHARDS_NPM_PUBLISH == 'true'` and a tag run | publishes both pre-checked tarballs with `--tag next` using the `NPM_TOKEN` secret; fails loudly if enabled with no token; skipped otherwise |

To cut a release: bump `version` (and regenerate `.claude-plugin/marketplace.json` with `node -e "require('fs').writeFileSync('.claude-plugin/marketplace.json', require('./build/package').marketplaceText())"`; the drift test fails otherwise), commit, `git tag v<version> && git push origin v<version>`. To enable npm, set the variable and secret in the repo settings. A manual dispatch only builds and uploads artifacts unless `push_marketplace` is set.
